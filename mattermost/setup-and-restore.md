# 홈서버 Mattermost 스택을 git 하나로 묶고 setup.sh 로 복원하기

홈서버(Mac mini)에서 Mattermost 를 몇 달 굴리다 보니 이상한 점이 보였다. 앱 코드는 전부 git 에 있는데, **정작 서버를 지탱하는 쪽은 git 밖**에 있었다.

| 대상 | git |
|---|---|
| 훅 서비스, Claude 봇, Copilot 봇 | 없음 |
| Mattermost docker-compose, nginx 설정 | 없음 |
| Mattermost MCP 서버(서드파티 포크) | 있음, 하지만 원본 저장소 |

디스크가 죽거나 설정을 잘못 고치면 되돌릴 방법이 없었다. 웹훅 주소가 잘못돼 있던 것도 "언제 바뀌었는지" 알 수 없었다. 그래서 전부 한 저장소로 묶고, **새 PC 에서 clone 후 `setup.sh` 한 번**으로 같은 구성이 서도록 만들었다.

## 저장소를 어떻게 나눴나

도구 스크립트 모음 저장소와는 **분리**했다. 스크립트 저장소는 파일 몇 개짜리 도구를 모으는 곳이고, Mattermost 는 빌드·`node_modules`·배포가 있는 앱 코드다. 섞으면 clone 이 무거워지고 관리 기준이 흐려진다. 서버, 봇, 훅, MCP 는 포트와 설정을 공유해서 한 단위로 복원해야 하기도 하다.

```
mattermost-repo/
  server/           docker-compose, 서버 설정(config.json)
  nginx/            nginx.conf
  hooks/            Jenkins·GitHub·Play 알림 웹훅 서비스
  claude-bot/  copilot-bot/
  mcp/  claude-channel/   서드파티 포크 사본
  launchd/          로그인 시 자동 시작 plist
  scripts/          DB 백업·복원
  ecosystem.config.js     pm2 설정
  setup.sh
```

서드파티 포크 두 개는 `.git` 을 떼고 소스만 복사한 뒤, 출처와 원본 커밋을 README 에 남겼다. 이력은 원본 저장소에 있으니 이쪽에서는 "복원에 필요한 소스"만 갖는다.

## setup.sh 가 하는 일

```
deps → server → build → pm2 → nginx
```

1. **deps**: brew 로 node, nginx, colima, docker, docker-compose 설치, npm 으로 pm2 설치
2. **server**: Colima 시작 → compose 파일 배치 → 서버 설정 심기 → `docker-compose up -d` → 응답 대기
3. **build**: 서비스별 `npm ci` 와 `npm run build`
4. **pm2**: `ecosystem.config.js` 로 훅과 봇 시작, `pm2 save`
5. **nginx**: 인증서 복사 → 설정 교체 → `nginx -t` 통과 시에만 재시작

여러 번 돌려도 안전해야 해서 설정 파일을 덮어쓰기 전에는 `.bak-시각` 으로 백업하고, 이미 있는 것은 건드리지 않게 했다.

## 부딪힌 문제들

### 1. 서버 설정(config.json) 복원

Mattermost 는 봇 계정 허용, 사용자 액세스 토큰, 웹훅과 슬래시 명령, 플러그인 설정을 `config.json` 에 둔다. 이 파일이 named volume 안에 있어서 compose 만으로는 복원되지 않는다. 플러그인 본체는 이미지에 내장돼 첫 기동 때 자동 설치되므로 설정만 옮기면 된다.

처음에는 파일을 바인드 마운트해서 볼륨에 복사하려 했는데 `No such file` 이 났다. **Colima 를 `--mount` 로 외장 SSD 만 지정해 띄웠더니 홈 디렉터리가 컨테이너에 마운트되지 않았던 것**이다. 그래서 표준입력으로 흘려 넣는 방식으로 바꿨다.

```bash
docker run --rm -i --user root -v "$vol:/c" postgres:16-alpine sh -c \
  'if [ -f /c/config.json ]; then cat >/dev/null; echo "이미 있음 — 유지"; \
   else cat >/c/config.json && chown 2000:2000 /c/config.json && chmod 640 /c/config.json; fi' \
  < server/config/config.json
```

- 이미 `config.json` 이 있으면 덮어쓰지 않는다(운영 중 설정을 날리지 않기 위해).
- 소유자는 Mattermost 컨테이너 사용자(2000)에 맞춘다.
- `sh` 가 없는 mattermost 이미지 대신, 어차피 compose 가 받는 `postgres:alpine` 을 재사용했다.
- 임시 볼륨으로 시험해서 크기, 소유자, 두 번째 실행 시 유지됨을 확인했다. 운영 볼륨은 건드리지 않았다.

### 2. 인증서

도메인은 무료 DDNS 를 집 IP 에 직접 연결하는 구조라 포트포워딩, nginx, Let's Encrypt 가 모두 필요하다. Cloudflare 는 다른 도메인의 터널에만 쓰고 있어서 이 경로와 상관이 없었다. 인증서는 갱신 스크립트를 가진 다른 저장소에 두고, `setup.sh` 가 그 저장소를 찾아 복사한다. `live/` 의 심볼릭 링크는 링크로 복사되는지, 개인키 권한이 600 인지 임시 홈에서 확인했다.

### 3. 라이브 설정의 오타

저장소로 옮기려고 운영 중인 `nginx.conf` 를 읽다가 `/hooks/` 블록에서 `\$host`, `\$remote_addr` 처럼 **변수 앞에 역슬래시가 붙은 줄 4개**를 발견했다. heredoc 에서 복사하다 생긴 흔적으로 보인다. 동작은 하고 있었지만 헤더가 의도대로 안 넘어가고 있었을 것이다. 백업 후 고치고 `nginx -t` 와 `reload` 를 한 뒤, 훅, Mattermost ping, 봇 API 가 전후로 모두 200 인지 확인했다. **git 에 올리기 전에는 아무도 못 봤을 버그**였다.

## 혼자 검증하면 놓치는 것: 교차 검증

`setup.sh` 는 지금 돌아가는 서버와 포트가 겹쳐서 이 PC 에서 통째로 실행해 볼 수 없다. 그래서 정적 분석으로 최대한 걸러냈다.

- `shellcheck` 로 정적 분석
- 다른 모델(Copilot)에게 "새 PC 에서 처음 실행하는 시나리오를 줄 단위로 시뮬레이션하고 처음 막히는 지점을 찾아라"고 요청

두 번의 리뷰에서 나온 지적 중 실제 결함으로 확인해 고친 것들이다.

- nginx 검증이 실패하면 메시지만 찍고 종료 코드는 성공이었다 → 설정을 복구하고 비정상 종료
- 서버가 안 떠도 경고만 하고 계속 진행했다 → 즉시 종료
- `all` 이 nginx 단계에서 죽으면 pm2 까지 못 갔다 → nginx 를 맨 뒤로
- 빈 DB 에서 봇 토큰이 무효라 pm2 가 재시작을 폭주시킬 수 있다 → 지수 백오프(`exp_backoff_restart_delay`)
- DB 복원이 중간에 실패하면 Mattermost 컨테이너가 멈춘 채 남는다 → `trap` 으로 재시작
- 백업 출력 경로가 `cd` 이후 기준이라 덤프가 엉뚱한 곳에 생긴다 → 절대경로로 변환
- compose 파일을 백업 없이 덮어썼다 → 다르면 백업

지적을 그대로 받아쓰지는 않았다. 컨테이너 이름이나 compose 서비스명처럼 리뷰어가 파일을 못 보고 **가정한 부분**은 직접 compose 를 열어 확인했다(`postgres`, `mattermost` 가 맞았다).

## 알림은 용도별 채널로 나눈다

복원 이후에 알림 경로도 정리했다. 채널마다 Incoming Webhook 을 하나씩 두고, 보내는 쪽이 웹훅 주소만 알면 된다.

| 채널 | 들어오는 것 |
|---|---|
| 크래시 알림 | Crashlytics 폴러가 감지한 크래시 |
| 배포 | Jenkins 빌드·배포 성공/실패 |
| 봇 대화 | Claude, Copilot 봇 |

**Crashlytics 조회 실패가 계속 올라왔다.** 하루에 한 번만 알리게 만들어 뒀는데도 반복됐다. 원인은 둘이 겹친 것이었다. Firebase API 가 간헐적으로 `HTTP 500` 을 주고, 폴러가 조회에 성공할 때마다 상태를 새로 만들면서 "마지막 경고 시각" 을 같이 지웠다. 실패와 성공이 번갈아 오면 제한이 매번 풀린다. 경고 시각은 성공해도 유지하고, 연속 3회 실패했을 때만 알리도록 바꿨다.

**Jenkins 알림을 Discord 에서 Mattermost 로 옮겼다.** 파이프라인은 이미 "결과 데이터(facts)를 만들고 렌더러가 채널 형식으로 바꾸는" 구조라서, 렌더러 하나를 바꾸는 일이 됐다. 메일 폴백 규칙(채널이 실패하면 메일)과 테스트는 그대로 두고 기대값만 갱신했다. 처음에는 별도 호출을 하나 더 붙였다가, 같은 알림이 두 갈래가 되는 구조라서 렌더러 교체로 다시 정리했다.

두 가지를 배웠다.

- **파이프라인 정의가 어디서 읽히는지부터 확인한다.** 앱 저장소에 `Jenkinsfile` 이 있어서 그걸 고쳤는데, 실제 잡은 별도 저장소의 파이프라인을 읽고 있었다. 헛수정을 하고서야 잡 설정에서 알았다.
- **웹훅 주소의 경로 접두사를 시험한다.** 서버를 하위 경로로 서비스하면 주소 앞에 그 경로가 붙어야 한다. 빠뜨리면 리다이렉트되고, 클라이언트가 이를 따라가면서 요청이 조용히 사라져 응답은 성공으로 보인다. 직접 한 번 보내서 채널에 도착하는지 봐야 한다.

## 아직 남은 것

- **새 PC 에서의 전체 실행은 못 해 봤다.** 정적 분석과 부분 시험까지가 지금의 한계다.
- **대화, 계정, 채널은 DB 에 있다.** 코드와 설정은 저장소로 복원되지만 데이터는 `pg_dump` 백업과 복원 스크립트를 따로 돌려야 한다. 봇 토큰도 DB 의 봇 계정에 묶여 있어서 복원 전에는 봇이 인증하지 못한다.
- 첨부파일 볼륨은 별도 복사가 필요하다.
- 채널 이름 정리(기본 채널 처리)와 `/deploy` 슬래시 명령의 Jenkins 인증 갱신이 남아 있다.
- `pm2 startup` 이 출력하는 sudo 명령은 사람이 한 번 실행해야 한다.

## 정리

- 홈서버의 "git 밖에 있던 것들"을 한 저장소로 모으는 것만으로도 변경 이력과 백업이 생겼다.
- **볼륨 안에 있는 설정**은 compose 만으로는 안 따라온다. 무엇이 어디에 저장되는지(DB, 설정 볼륨, 데이터 볼륨)부터 나눠 보는 게 먼저다.
- 직접 돌려 볼 수 없는 스크립트는 `shellcheck` 와 다른 모델의 시뮬레이션 리뷰를 같이 쓰면 혼자 놓친 곳이 꽤 잡힌다.
- 비밀값은 비공개 저장소 전제로 함께 넣었다. 공개할 일이 생기면 `.env` 와 토큰은 반드시 분리해야 한다.
